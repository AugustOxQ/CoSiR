# RedCaps cross-dataset validation of the Family #2 win (change log, 2026-07-08)

Context: Impressions seed-replication + peak-finding confirmed Family #2 (buddy contrastive
supervision) as a real, dose-dependent win — λ_con=1.0 gives ~+2 R1 t2i / ~+3 R1 i2t at
lr=1e-3, lr_label=1e-4 (mean/SEM up to ~40 over 3 seeds), rolling over past the peak (λ_con=4
significantly HURTS). The one open threat: Impressions has near-duplicate scaffolding (814
source photos behind 12k records), so buddies may lean on same-photo near-dups. RedCaps-150k
is genuinely 1:1 → clean cross-dataset check.

## Discovery (why this needed setup, not just a sweep)
- RedCaps had NEVER been trained through this pipeline — prior "extended buddy analysis to
  redcaps" was graph ANALYSIS only (src/test/20260623_redcaps_buddy/redcaps_buddy.py).
- The stock `redcaps.yaml`/`redcaps2.yaml` point featuremanager.storage_dir at
  `/data/SSD2/pre_extract/redcaps/features`, which is EMPTY. The only extracted store is
  `/data/SSD2/pre_extract/redcaps_150k/features` (150k samples, CLIP ViT-B/32, complete),
  with matching `redcaps_150k.json`; in-domain test `redcaps_test.json` (25k 1:1 pairs) exists.
- Verified the pipeline is dataset-type-generic for RedCaps: `load_existing_features=True`
  loads the cached 150k features (no re-extraction); `CoSiRValidationDataset` parses only
  `image`+`caption` (both present, caption is str); the oracle retrieval metric
  (test_oracle/t2i_R1) is NOT impressions-gated (computed from per-sample conditions), so
  the analyzer works unchanged. Impressions-only branches (train_cosir.py 410/532/1059) no-op.
- Train/test images resolve on disk under /data/PDD.

Wires featuremanager.storage_dir → redcaps_150k store, train → redcaps_150k.json, test →

`dataset=impressions` → `dataset="${DATASET:-impressions}"` — one-line parametrization so the

## scripts/run_buddycon_redcaps.sh (NEW)
Fixes the confirmed operating point (lr=1e-3, lr_label=1e-4, dim=16, alpha=0.5) and runs the
minimal confirmation λ_con ∈ {0, 1.0} × seeds {1,2,3} = 6 runs, tag `buddy-con-redcaps`.
`SMOKE=1` → 2 epochs / 1 seed / λ_con=0 / eval-every-epoch (tag suffix `-smoke`) to de-risk the
never-before-trained pipeline; shares RESULTS_DIR so the expensive one-time 150k spectral buddy
template is built once and reused by the full sweep. EPOCHS: per-sample z updates once per epoch,
so epochs = updates-per-z, and z is the buddy-con term's substrate; too few epochs undertrains z
and collapses Δ → false null. Trajectory: initial 50 (wrong — false-null risk) → corrected to 250
(matches Impressions) → user set 100 for a next-day meeting deadline. 100 is a sound compromise:
enough z updates to engage the term, and being under 250 only makes it a CONSERVATIVE test (a
slightly-undertrained z can shrink the true Δ, never inflate it). Combiner weights train every
step (fine with fewer epochs). Cheap because features are cached (150k combiner steps/epoch);
one-time cost is the 150k template.

# B-leaning condition initialization (β affinity reweight) — added on user request
Motivated by `docs/reports/2026-07-08_heldout_grid.md`: across 6 held-out encoders × {B,E} ×
{Impressions,RedCaps}, the strict intersection B is a consistently cleaner buddy signal than the
union E, but init uses E. Added an OPTION to lean the init on B via a spectral-affinity multiplier.
Spec: `docs/superpowers/specs/2026-07-08-b-lean-init-design.md`. Mechanism: reweight (not a hybrid
graph); scope: init geometry only (buddy_edges.npy / λ_buddy regularizer unchanged = E). Default
b_weight=1.0 is byte-for-byte the old behavior (test_b_weight_identity is the regression gate).

## /src/conditional_buddy/embedding_methods.py
`spectral_embedding(...)` gained `b_edges: csr_matrix=None, b_weight: float=1.0`. After the affinity
is built (`A = 1 - dist`) and symmetrised, when b_edges given and b_weight!=1.0:
  Bm = symmetric-binary support of b_edges
  A = A + (b_weight - 1.0) * A.multiply(Bm)   # affinities on B edges scaled by b_weight
B ⊆ E so `A.multiply(Bm)` selects exactly the strict-buddy affinities; weights may exceed 1 (fine
for precomputed affinity). b_weight=1.0 ⇒ boost term is 0 ⇒ identical output.

## /src/conditional_buddy/compute_buddies.py
`compute_buddy_init(...)` gained `b_weight: float=1.0`. Now captures `A_img, A_txt` from
build_buddy_graphs (previously discarded) and, when b_weight!=1.0, builds
`B = binarize(A_img.multiply(A_txt))` and passes `b_edges=B, b_weight` to spectral_embedding. B is
in the same pre-reorder row order as E/D_mixed — correct alignment.

## /src/conditional_buddy/init_conditions.py
- `_buddy_cfg`: reads `b_weight` (default 1.0) from cfg.train.buddies.
- full path: passes `b_weight=bud["b_weight"]` to compute_buddy_init; records it in
  template_config["extra"]["b_weight"] for provenance.
- visualize path: computes B before the spectral_embedding call and passes
  `b_edges=B (if b_weight!=1.0), b_weight`.

## /configs/train/default.yaml
train.buddies: new `b_weight: 1.0` with comment (B-lean off by default; >1 pulls strict buddies
tighter).

## Tests — src/test/20260609_conditional_buddy/test_compute_buddies.py

+ test_b_weight_tightens_buddies: on two-cluster synthetic, mean emb dist over actual strict-B edges

# B-lean b_weight — training-path wiring + quick sweep (follow-up to the init option above)
The b_weight option first landed only in the standalone init_conditions.py runner. For a training
sweep it also has to flow through the train pipeline AND be part of the template cache key (else
every b_weight reuses the b_weight=1.0 template → silent no-op). Wired end-to-end + TDD'd.

## /src/utils/embedding_manager_nocache.py
`_buddy_init(...)` gained `b_weight: float = 1.0` and passes `b_weight=b_weight` to
compute_buddy_init. `initialize_embeddings_buddies` already forwards **buddy_kwargs, so the value
threads manager → initialize → _buddy_init → compute_buddy_init.

## /src/hook/train_cosir.py
- `_buddy_kwargs`: added `"b_weight": float(getattr(_bud, "b_weight", 1.0))` → passed to
  initialize_embeddings_buddies at training-time init.
- `_extra` (template-compat guard, used by BOTH store_imgtxt_template and load_imgtxt_template):
  adds `b_weight` to the key ONLY when != 1.0. Rationale: keeps pre-b_weight templates compatible
  for default runs (no gratuitous rebuild), while a changed lean still mismatches → rebuild. So a
  b_weight sweep never silently reuses another value's template.

## /scripts/run_blean_impressions.sh (new)
Quick B-lean sweep on Impressions built from the Family #2 (buddy contrastive) setup. b_weight is a
template key, so it's a BASH loop (default "1.0 4.0 8.0"), each value → its own results_dir
(bw_${BW}) + rebuilt template. Inside each, lambda_buddy_con {0,0.3} is a Hydra multirun that reuses
that b_weight's template (clean term ablation), mirroring run_buddycon_full.sh. SMOKE=1 → 2 epochs,
single cell. Quick-run defaults: EPOCHS=100, EVAL_INTERVAL=50, seed=42.
SMOKE validated (SMOKE=1 BWEIGHT_SWEEP_SMOKE=4.0): "[buddies] B-lean: b_weight=4.0, strict-B edges
nnz=19,178 (of E nnz=288,344)"; template_config extra.b_weight=4.0; train+eval exit 0.
